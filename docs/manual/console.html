Karakuri · the manual

The console is the instrument

Pick a Set per deck, mix them live, and see who is holding every control. Mixing lives between decks; shaping lives inside one. Every divider drags, because a preview's size is a machine's answer rather than a layout's — and the whole panel follows the room, pastel on white by day and lit on black in a dark hall. The grip in a bay's head says whose size you are setting: a bay with one is yours to size, and a bay without one is the height of what is in it. Both sides of a divider move either way; the grip says which side the number belongs to.

Three columns, and they are named because you address them: a left pane and a right pane, which fold away to give room, and the centre, which is what they give it to. Each holds a stack of bays — Library, Program, Mixer and the rest — and every bay below says what it is standing on. The middle one is not a third pane on purpose: folding it is not a thing anybody wants, and solo is.

The engine already said which one is the fader

An earlier draft drew gain and opacity as two identical sliders, which threw away a distinction the code states outright:

/// The level the material arrives at. Colour only.
pub gain: f32,
/// The fader across the blend, [0, 1]. The only one of the two that
/// touches what a layer covers.
pub opacity: f32,

They behave differently too: opacity at zero silences under every blend mode, and gain at zero does not silence over — a black card still covers. So this is a channel fader and a trim, as a mixer has always had them. Opacity is the tall control your hand lives on; gain is the small trim above it, set once and left.

The mixer is an L5, and so is a master effect

A master effect looked like a new kind of node. The engine already writes the signature down:

// The L5 node, nested: `[Texture] -> Texture`.

A master effect is that signature with one input; the mixer is the same with several. One kind, not two — what made the mixer look special is that its instance is built in, the third time this shape has come up: L3 has a built-in orbit camera and writable camera procedures, and the merge record describes the built-in L5 exactly as camera describes the built-in L3.

So admitting frame effects is giving L5 a writable form, not extending the algebra. Fan-in is already solved by uses plus edge; a per-deck effect and a master effect become the same node at different points; and the deck count stops being a system constant, since how many inputs an L5 folds becomes a property of the procedure rather than of one built-in shader. Feedback is the exception: reading the previous frame is a cycle, and wants a decision of its own.

What each region is standing on

Mixer

Four channel strips, all visible, nothing that scrolls out of reach mid transition. Four today because the compositing shader declares four inputs — the strip is a paged list whose length is a number, and the header says which page you are on.

Inspector

n panes, each showing whatever you point it at. Parameters group by node, the way a Set is addressed everywhere else (L2:0:amount), so an effect layer's controls need no second idea of where things live. Only what a Set publishes — the reason this is four rows rather than twenty-five.

Who is holding a control

A bound parameter shows its source instead of a number: a signal, a MIDI control, a sequencer lane, an agent. That readout is where disagreeing with the system begins — a control you cannot see being moved is one you cannot take back — and take back sits right beside it.

A knob is bound to a deck, not to a Set

A MIDI control is learned against the deck and the position in its published interface — knob 3 is knob 3 whatever Set is loaded — which is why the inspector numbers its rows. Binding to a Set's parameter by name would make the mapping a cost you pay again on every swap, and a learn flow exists precisely to make it a cost you pay once. It also settles the crossing: the same Set loaded into two decks is two addresses, because the deck is in the address.

The order is what the Set published, and where it published nothing, the order its parameters were declared. Publishing is already the author deciding what is worth showing; deciding the order is a small extension of a decision they are making anyway. A map is a file — which knob is which belongs to the hardware in the room, so it is saved and recalled per controller and never travels inside a session.

Two focuses, and they do not look alike

The deck selection persists — it is what a key press is addressed to, and it stays put when you tab away into the library. Keyboard focus is transient and goes wherever tab lands. Drawing them the same way would erase which of the two a reader is looking at, so the selection is a solid ring and focus is a dashed one.

Authority is per node

man / sug / auto on each node head, never a global mode. Manual is yours alone, suggest proposes into the staging lane, auto acts. One of the four properties the whole system is defined by, so it belongs on the face of the panel rather than in a preferences window.

Health, in the transport

Frame time against the budget, and what the last write did — landed, rolled back for cost, or failed to build. The rollback already happens on its own; what was missing was any way to see that it had. Unbreakable on stage is only reassuring if it is visible.

Sequencer

One row per lane. The row keeps its width and the cells divide it, so eight steps are landscape cells and sixteen are portrait ones. Each lane sits under the mixer strip it drives. A lane is a binding — a source, a target, a curve and a range, a record that already exists — so a lane drives a Set parameter as readily as a deck fader.

Library, and staging under it

A scope and a walk, not one flat list: favourites, my sets, app presets, a folder — and the scope list is itself extensible. Staging is where candidates wait, whether they came from you or from an agent; a rejected one costs nothing, because the previous artifact is still in the library.

Program, sized by height

A 16:9 view filling a wide centre column would be 763 pixels tall and eat the inspector whole. So you drag its height and it letterboxes into the width it has — which is what the engine already does. Height given back is rows in the library and the inspector, which are the two bays that take it.

The bay is two regions and they fold apart. The picture is a sink, listed in Outputs as program view, and it is on screen exactly when that sink is on — so there is no state where it is hidden and still costing a pass. The deck previews under it are auditions of their own, so they stay when it goes.

The picture carries no label of its own. The bay head already says Program, and this is a region somebody may be capturing: a capture that is neither the canvas nor a clean crop of it is worse than useless, and a word burnt into the corner is exactly that. The A–D under it keep their letters, which are outside anything you would capture and are the only thing naming a deck.

Outputs

Every place a composited frame goes, as one switchable list. A projector window is a second sink and lives in the repository; Syphon, Spout and NDI are plugin sinks and appear only when a plugin is loaded. Fullscreen is just what an application does. The picture in the Program bay is a sink like any other and is the first row.

All of them may be off, and that is a state worth having. The deck previews are auditions rather than outputs, so with every sink off you can still see the decks and work on them — which is what setting up before doors is. Nothing is refused here, so nothing has to be explained: a control that quietly declines the last of something is a rule an operator can only find by experiment.

Every icon explains itself

Density is only earned if it is legible on demand, so hover says three things: what the control is, what state it is in, and what a click will do. The third is the one usually left out, and leaving it out is what makes a compact panel unlearnable — the reader sees the state and never learns it is a control. The tooltip also carries the control's MIDI assignment, which is how learning one works: point at anything with a tooltip and move a knob. Coverage then takes care of itself — a new operation gets a tooltip, and a tooltip is a thing a map can reach.

One vocabulary, four ways in

Every operation is reachable from the GUI, from the keyboard alone, from a mapped MIDI control, and from MCP. That is structural before it is visual: each operation is named once, and every surface routes into that name. An operation only the mouse can reach breaks it; so does one the map cannot address. The sequencer is a fifth route, and it only works for the same reason.

GUI → command keys → command MIDI map → command MCP → command sequencer → command

It is checkable rather than merely intended: with the vocabulary exhaustive, a test asserts that every command carries a key binding, is addressable by the map, and is what the GUI emits. And it is half-built — L4:1:exposure is already one spelling shared by --param, --publish, the MIDI map and the MCP tools. So this milestone opens with naming, not drawing.

Still open

Whether a folder scope reads Sets or artifacts

A directory of .kir files is a different thing from a directory of Set files, and a bundle is a third. The scope list is where that difference becomes visible, so it wants deciding before the first scope beyond the store is added.

How a Set gets from the library to a deck

Dragging a row onto a strip is one answer. A focused deck and a load key is the one that also satisfies keyboard-only operation — and the constraint should decide it, with dragging added afterwards as a second route to the same command.

A layout, not a specification — it is what the implementation is checked against. The mechanisms behind the mixer, the inspector, the library and the outputs are built; the master chain, the sequencer, the staging lane, authority and the panel itself are not. The seven rules are what all of this obeys.
