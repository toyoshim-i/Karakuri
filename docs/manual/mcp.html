Karakuri · the manual

A partner that shares the console

Karakuri treats AI pair-programmers as co-performers. Over the Model Context Protocol (MCP), an assistant can inspect what each deck is playing, re-wire modulation graphs, edit shader procedures on the fly, and trigger musical operations — all subject to safety gates and live mixer tracking controlled directly from the performance console.

Connection & Protocol Architecture

Karakuri exposes an MCP server over HTTP JSON-RPC on the loopback interface when launched with the --mcp PORT flag: 

karakuri --mcp 8080

Any standard MCP client (Claude Desktop, Cursor, Gemini, or custom scripts) can connect to the endpoint http://127.0.0.1:8080/. Every interaction obeys the core architectural invariant: a surface offers, it never decides (Principle 0090). An agent dispatches standard operations through the same permission gates that govern keyboard and MIDI controls.

The Permission Model & Safety Gates

Live visual performances cannot tolerate broken shaders or rogue edits on material currently projected on air. Karakuri provides a two-tier safety mechanism:

1. Bay Class Openings

Console bay heads feature dedicated class toggle capsules. An operator opens or closes permissions per functional section:

  • LiveDeck (Program bay): Enables or restricts operations that directly swap active deck procedures.
  • MixFaders (Mixer bay): Authorizes changes to mixer opacity faders, trims, and blends.
  • MasterEffects (Master bay): Governs global shader effects and color balance.
  • InputsAndOutputs (Outputs row): Controls projector assignments and audio-in routing.

2. Slot MCP Policies (Auto / On / Off)

Each deck slot wears an explicit MCP policy pill in the Inspector bay head:

  • Auto (Default): The slot is freely editable while parked or rehearsing. The moment the mixer fader rises or the slot goes on air, it becomes automatically write-protected to safeguard the live projection.
  • On: The operator explicitly grants live live-coding access to this slot, even while contributing to the main screen mix.
  • Off: The slot is strictly locked against all agent modifications regardless of fader position.

The M7 Co-Performance Tool Suite

Collaborative live coding requires rapid discovery and atomic staging. Three specialized workflow tools form the core of the agent loop:

01

get_permissions — Discover current constraints

Returns the open/closed status of all bay classes, per-slot policies, real-time mixer contribution state (in_mix), and whether each deck slot is currently writable. Agents query this before planning edits to avoid rejected roundtrips.

02

read_slot — Full slot procedural inspection

Fetches all active procedural layers (L1 material, L2 deformation, L3 camera, L4 renderers, and Field distance functions) for a deck slot in a single call.

03

copy_slot — Safe rehearsal & duplication

Copies the complete procedural setup from one slot to another with atomic staging. A common workflow is copying a live slot (e.g. Deck A) to an off-air slot (e.g. Deck B), modifying it safely with the agent, previewing the result, and transitioning it live with the crossfader.

Complete MCP Tool Catalog

Procedure Authoring

  • read_procedure: Reads the .kir shader source for a specific slot, layer, and index.
  • write_procedure: Submits revised source code. Compiles on a background worker thread, swaps at a frame boundary, and monitors GPU render budget for 30 frames. If it exceeds frame time, it automatically reverts.
  • check_procedure: Statically validates syntax, types, and execution costs without touching GPU memory or changing state.

Set Management

  • read_set: Inspects Set configuration, knob mappings, and node assignments.
  • list_sets: Catalogs available Sets in the library with optional text or tag filters.
  • save_set: Commits active deck parameters to a new or existing Set file.
  • check_set: Validates Set configuration and asset availability without activation.

Graph & History

  • wire_input: Connects modulation sources or audio-in channels to node inputs.
  • walk_history: Reads compilation and revision history for a Set, allowing previous versions to be recalled.
  • swap_outcome: Checks the compilation and performance measurement verdict of a background shader swap.

Performance Control

  • operate: Dispatches any of the 64 vocabulary operations from docs/manual/operations.html, fully verified against console permissions.

Atomic Staging & Scratch Directory Safety

When an agent modifies or copies procedures, files are written first to temporary files (.kir.tmp) and swapped via atomic filesystem rename (scratch::write_atomic; ADR-0363). This prevents file watchers and background compilers from reading truncated ASTs or observing torn writes during multi-file interface updates.
