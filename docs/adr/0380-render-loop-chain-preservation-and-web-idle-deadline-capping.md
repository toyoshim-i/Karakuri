# Render loop chain preservation and web idle deadline capping

## Context

In live performance rendering, visual presentation must be continuous ([P-0094](../principles/0094-the-show-does-not-stop-it-does-not-go-quiet-and-it-does-not-leave-the-operators-hands.md)). During testing of deck playback and idle states across native and Web (WASM) targets, two distinct render stalls were observed:

1. **Native redraw chain drop on early frame returns:**
   In `crates/karakuri/src/app/handler/redraw.rs`, the rendering handler throttles rendering when the frame interval is under 4ms (`if elapsed < MIN_INTERVAL { return; }`) and skips presentation if the surface texture is suboptimal or unavailable (`surface::Acquire`). In these early return paths, `gfx.window.request_redraw()` was not invoked. When deck playback was paused or transport was idle, the event loop transitioned to `ControlFlow::Wait`, stopping all future redraws until an external host window event (such as cursor movement) woke the loop.

2. **Web event loop starvation on `ControlFlow::Wait`:**
   In `crates/karakuri-web/src/app.rs`, when the Winit event loop entered `ControlFlow::Wait`, the browser runner ceased scheduling `requestAnimationFrame` callbacks. The WebGL/WebGPU surface effectively froze unless mouse or keyboard DOM events were continuously generated by the user.

## Decision

1. **Unconditional redraw chain preservation in handler:**
   In `crates/karakuri/src/app/handler/redraw.rs`, ensure every early-exit branch (including the sub-4ms frame rate cap and skipped surface acquisitions) re-schedules `gfx.window.request_redraw()` whenever live animation, deck playback, or background compilation requires ongoing updates.

2. **Deadline-capped idle waiting on Web:**
   In `crates/karakuri-web/src/app.rs`, clamp `ControlFlow::Wait` to a maximum timeout (32ms). When the runner would otherwise idle indefinitely, an explicit timeout ensures the event loop resumes autonomously, polling pending async tasks and servicing render requests without operator intervention.

## Consequences

- Redraw starvation is eliminated; displays update continuously at target frame rates on both native desktop and Web targets without requiring mouse movement.
- Real-time engine status (such as audio meters, transport counters, and async compilation spinners) remains responsive when decks are idle or stopped.
