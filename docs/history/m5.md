# M5 — Interface

**A milestone in progress.** This document is the historical record of what was planned, what was built, what decisions were taken on the way, and what has closed.

**It is not the present tense**, and nothing should cite it as though it were. What is in force is [docs/principles/](../principles/); what is active or owed is [roadmap.md](../roadmap.md); why a particular thing was decided is [docs/adr/](../adr/). A source comment must never point here — see `docs/contributing.md` §4.

Anything this milestone leaves owed is tracked in [roadmap.md](../roadmap.md).

---

**Goal:** The application. Karakuri is a GUI application for playing a VJ set in real time — picking a Set per deck and mixing them live.

**Exit condition:** Everything described in [`docs/manual/`](../manual/) is implemented — no `plan` badge left in the panel column of [every operation](../manual/operations.html) ([ADR-0226](../adr/0226-m5-closes-when-the-manual-is-implemented-and-the-meter-is-progress-rather-than-completion.md)).

## Foundation & Architectural Work Completed

Before individual bays were completed, M5 established the structural and architectural foundations across multiple crates:

### 1. Unified Operation Vocabulary & Surfaces
- **Single Vocabulary ([ADR-0180](../adr/0180-the-operation-vocabulary-is-a-crate-with-no-dependencies.md))**: Every operation is named once in `crates/karakuri-operation/` with zero external dependencies.
- **Surface Routing**:
  - `crates/karakuri-operation-record/` translates operations to disk-serializable and replayable records ([ADR-0194](../adr/0194-where-an-operation-becomes-a-record-is-a-crate-that-depends-on-both.md)).
  - MIDI mappings route into the same operations ([ADR-0196](../adr/0196-a-map-line-names-a-state-and-an-old-line-is-refused.md)).
  - MCP translates directly into operation calls ([ADR-0199](../adr/0199-mcp-names-its-operations-and-performs-them-itself.md)).
  - The console UI emits `panel::Op` values translating to the same vocabulary ([ADR-0197](../adr/0197-the-consoles-op-stays-and-what-blocks-it-is-the-page-rather-than-the-code.md), [ADR-0204](../adr/0204-the-root-and-the-body-row-stay-unnamed-and-a-folded-root-is-not-hit-testable.md)).
  - MCP safety gate ([ADR-0235](../adr/0235-mcp-reaches-every-operation-and-what-could-stop-the-show-is-refused-until-the-operator-opens-it.md)) audits operations and requires explicit operator opening for disruptive actions.

### 2. Standalone Application Binary
- **Binary Extraction ([ADR-0214](../adr/0214-the-program-moves-out-of-the-cli-and-two-thin-binaries-sit-over-it.md))**:
  - The main GUI window loop and renderer host was extracted from `karakuri-cli` into its own dedicated binary crate `crates/karakuri`.
  - Common runtime environment initialization moved to `crates/karakuri-environment` ([ADR-0215](../adr/0215-the-package-is-karakuri-environment-and-a-module-belongs-if-what-it-deals-with-is-outside-this-process.md)).

### 3. Layout Engine & Dynamic Arrangements
- **Immediate Layout Solver**: Built the zero-allocation, immediate-mode constraint solver in `crates/karakuri-layout`. *(This line previously cited ADR-0181, which is a different record — the picture's shape and the console's leftover. Which record decided the solver's shape is not established here; [ADR-0156](../adr/0156-the-consoles-arrangement-is-a-tree-this-repository-owns.md) is where the arrangement became this repository's tree.)*
- **Two-bit Node State ([ADR-0183](../adr/0183-a-node-is-out-of-the-layout-for-two-reasons-and-they-are-two-bits.md))**: Solved layout visibility via independent operator-folded and drawer-aside bits.
- **Arrangement Persistence ([ADR-0221](../adr/0221-an-arrangement-is-named-by-the-operator-and-kept-in-a-fourth-place.md), [ADR-0208](../adr/0208-resetting-is-the-default-case-of-restoring-an-arrangement.md), [ADR-0158](../adr/0158-a-saved-arrangement-that-disagrees-with-itself-is-refused-not-repaired.md))**: Operator window layouts and divider positions are saved under a name in a fourth place under the store, restored, and refused rather than repaired where a saved arrangement disagrees with itself. *(This line previously cited ADR-0219, which is the crossfader's record.)*

## Sub-Milestone Progress & Completed Bay Work

The work of M5 was partitioned by bay into M5.1–M5.9, followed by cross-cutting concerns (M5.10–M5.12).

### M5.1 — Program Bay (Completed & Re-engineered)

The Program bay is the central visual output and audition monitor for the console.

#### Work Completed
1. **Full GUI Surface Implementation**:
   - Central Program Picture sink with letterboxing and aspect-ratio preservation.
   - Four Deck Preview cells (A–D), showing active auditions or mixed master output.
   - MCP safety status capsule and arrangement solo pill in the bay head.
   - Interactive divider bar between the program view and preview row.

2. **Dynamic Arrangement & Preview Sizing Coherence ([ADR-0239](../adr/0239-the-program-bay-preserves-preview-size-when-arranging-beside.md))**:
   - **Superceded ADR-0182**: Previously, Beside arrangement inflated preview cells to half the bay height, discarding user sizing and consuming excessive horizontal space.
   - **Preview Size Preservation**: In Beside mode, cells retain the height and 16:9 width configured by the operator dragging the divider bar in Below mode.
   - **Pure Geometric Decider**: Replaced hardcoded width overrides with pure geometric area comparison (`area(beside.picture) > area(below.picture)`). The mathematical crossover boundary occurs at **706px** Program body width (1484px window width at default outer pane sizes).
   - **Initial Layout Ergonomics**: Re-proportioned outer pane default widths (Left: 340px, Right: 400px), yielding an initial central bay width of ~644px on standard 1440×900 displays. This ensures consoles naturally open in **Below placement** with the divider bar active, transitioning smoothly to Beside mode when expanded or dragged.

3. **Multi-Sink Frame Presentation**:
   - Supported independent slot target rendering and preview sinks through `Deck::slot_view` and tone-mapped bind groups.
   - Corrected `Record::Preview` routing to drive `Deck::set_preview` auditions. *(Superseded within the same sub-milestone by item 4: the record and its routing were removed once the operation behind them was retired. The cells draw from `Deck::slot_view`, which is the half of this item that stands.)*

4. **Resolution of Owed Rows and Retirement of Operations ([ADR-0240](../adr/0240-the-output-shows-the-mix-and-residency-keys-belong-to-the-mixer.md))**:
   - **`Put a deck on air, prime it, or take it off` Keybinding Retired**:
     - *Decision*: The key shortcuts (`space, w`) previously planned for toggling deck residency were evaluated and retired.
     - *Rationale*: Controlling whether a deck is live, priming, or parked is fundamentally the Mixer bay's operational role (via strip controls and tally chips), rather than a keyboard-driven Program bay responsibility. The key column in [`docs/manual/operations.html`](../manual/operations.html) was changed from `plan` to `gap &mdash;`.
   - **`Choose what the output shows` Operation Retired**:
     - *Decision*: The operation *Choose what the output shows* (`Operation::SetPreview`) was retired entirely and deleted from [`docs/manual/operations.html`](../manual/operations.html).
     - *Rationale*: With ADR-0239 establishing that the central Program Picture always displays the composited master output and the four dedicated Deck Preview cells continuously monitor their respective channels, switching the primary master canvas to audition a single deck became redundant and unnecessary. The function itself was judged superfluous, removing the operation from the manual and vocabulary.
     - *Extent of the retirement*: `Operation::SetPreview` and its gate class arm; the `karakuri-operation-record` conversion; `Record::Preview` in `karakuri-store` and the `Change::Preview` it decoded into, on the grounds that switching a preview is a bay-internal move rather than an engine one and so has nothing to record; the `preview` target in the MIDI map grammar and the five lines in `examples/surface.map` that used it; the `v` key in `karakuri-cli`, whose `--demo lines` script now fades one slot out at a time instead; and the press on the console's four preview cells, which stay claimed controls and keep drawing. `crates/karakuri` aims a sink per cell while that deck is Live, which answered the roadmap's open question about what deck A's cell shows. `Deck::set_preview` and `Deck::preview` remain in `karakuri-engine` with no caller in the workspace. *(Both of those last two sentences were superseded within the same sub-milestone, by item 5. The residency gate on the aim was removed, and `Deck::set_preview` and `Deck::preview` were deleted rather than left uncalled.)*

5. **Residency Removed from the Aim, and the Command Line Scoped Out ([ADR-0242](../adr/0242-the-command-line-is-test-tooling-and-the-instruments-principles-do-not-bind-it.md), [ADR-0243](../adr/0243-the-program-picture-is-an-output-and-the-four-cells-are-monitors.md))**:
   - **The `Residency::Live` gate deleted**: `Deck` draws every slot into its own target every frame whatever its residency, and `Engine::aim` gates a cell on whether there is a slot behind it. This closed the second of the two P-0080 gaps ADR-0241 left, and `Deck::set_preview` and `Deck::preview` were deleted with it.
   - **The first gap was scoped away rather than closed**: ADR-0242 makes `karakuri-cli` test tooling and states that a principle written for the person playing the instrument does not bind it, so a command line that cannot audition a slot fails no rule. P-0080 now states its own scope.
   - **The bay's model recorded**: ADR-0243 settles that the Program picture is an output — the set `Operation::RouteFrame` has to name — and that the four cells are monitors, welded to their letters, which nothing routes.
   - **The caption band**: a cell's letter and state moved out of the image into a caption under it — the deck's letter, one word for what the cell is showing (`material`, or `no slot`), and a place kept for the risk badge. `karakuri-console`'s `caption_of` derives the band from the image rectangle rather than taking it beside one, so `preview_rects`, which is what the engine sizes a texture from, stayed the image and never the image plus its label. The badge was not drawn at the close, because nothing in the workspace estimated what a slot costs.
   - **And ADR-0240's stated reason for retiring *Choose what the output shows* is not the reason.** It said redundancy with the four cells. ADR-0243 settles the model instead: the picture is one of the outputs, so once material is on it, it is the broadcast of the final result and never a preview of anything, and the four cells are welded to the letters under them. An operation that pointed the output at a deck was wrong from the start rather than made redundant. `Operation::RouteFrame` names the picture and can never name a cell, which is one more constraint on M5.6's naming question — restated beside M5.1's entry in [roadmap.md](../roadmap.md).
   - **The panel serves MCP**: `karakuri --mcp PORT` runs `karakuri_environment::mcp::serve` against the panel's own `Opening` and publishes seven tools, and `Live::save_set` gave this program a save path it did not have.

#### M5.1 Exit, met on 2026-09-03

- **No `plan` badge in either column for this bay's rows.** The board — `grep -o 'rt plan">panel <b>[^<]*' docs/manual/operations.html` — returns inspector, master chain, library, transition row, staging, transport, outputs and the rest, and names no control of this bay. - **The bay's prose is on its controls.** The three notes are condensed into `data-tip` attributes in [`docs/manual/console.html`](../manual/console.html). ### M5.2 — Mixer Bay (Completed, Re-opened, and Completed Again)

The Mixer bay is the deck as strips: a trim, a fader, a blend button, a meter and a mask mini per deck the session has, with the transition row under them.

#### Work Completed

1. **The transition row, which was painted by nothing**:
   - `.xfade` existed in the mock and no code drew it. *Choose the wipe shape, the quantum, the length* went first inside the bay and is what made the row real: the console owns the quantum, the length and the wipe shape as a pointer of its own — `View::transition` — and emits `Operation::SetTransition` from three pills.
   - **The other rows converted only once a surface held what they set.** *Fade a deck out or in* answered `Owed::NotRead(Reading::Transition)` until the transition settings were handed over, and *Choose which renderer of a deck is live* and *Wipe the next deck in* read the same way, the wipe reading the row's third setting — its front shape — as well as the other two. *(Superseded after this sub-milestone closed: `crates/karakuri/src/main.rs`'s `reading` now answers the transition settings and the mix, and the `go` capsule is the one reading that takes three — the settings, the arriving deck's mask, and where that deck already sits in the mix.)*

2. **The one row that was blocked, and who answered it**:
   - *Wipe the next deck in* was the one row of the eight that was blocked, and it waited on who says the front shape and the soft edge are its. **Both got an owner.** The shape is `Operation::SetTransition`'s third setting and reaches the conversion inside `Current::transition` beside the quantum and the length; the soft edge is read off the mask already running on the deck being wiped in.
   - `written(Wipe)` writes its six records — four or five where the deck arriving is already under `over` or already live, because the mode is the operator's and a wipe does not take it back — and `karakuri-cli`'s `c` is one `operate` call. What the panel's row needed was therefore the control and not a decision.

3. **A fade has no control on a strip, decided on 2026-09-05**:
   - *Fade a deck out or in* became a `gap` rather than a `plan`. A fade is an opacity moved over a few seconds and the fader is already the control for moving one, so a capsule asking for the same move would take permanent room on a strip to save the gesture the strip is built around.
   - **What it would have bought is the one thing a hand cannot do** — landing the move on the beat rather than near it — and that was judged not worth a control here.
   - The argument an operator reads is *Nothing on a strip starts a fade* on [the console page](../manual/console.html), beside *The mixer has no crossfader*, which is the same shape of decision and was the precedent for the `gap`.

4. **A row that was counted here and was never this bay's**:
   - ***Choose which renderer of a deck is live* moved to M5.5 on 2026-09-05.** The mock draws `rend-row` in the **Inspector** and nowhere in the Mixer, and [the console page](../manual/console.html) describes it and *Composite a deck's renderers* as one thing — *"Composite is the deck's, and the renderer chips below are what it turns into a choice"* — while that other half was already counted under M5.5. Split across two sub-milestones, the chips would have been built first and meant nothing until the toggle above them existed.
   - Its `plan` key badge (`r`) went with it, and is [ADR-0259](../adr/0259-the-keyboard-is-addressed-to-the-bay-that-has-focus-and-a-global-letter-is-a-convenience-or-the-operators-own.md)'s rather than that bay's.

5. **The key column, and why closing short of the stated exit was deliberate**:
   - Four rows kept a `plan` key badge — *Fade a deck out or in* (`f g`), *Crossfade to the next deck* (`x`), *Wipe the next deck in* (`c`) and *Choose the wipe shape, the quantum, the length* (`z n j`). *Fade a deck out or in*, *Choose which renderer of a deck is live* (`r`) and *Choose the wipe shape, the quantum, the length* named letters the binary already binds to folding, resetting and unfolding: the collision [ADR-0220](../adr/0220-the-key-column-is-the-instruments-keyboard-and-the-clis-keys-are-its-own.md) recorded and did not resolve.
   - [ADR-0259](../adr/0259-the-keyboard-is-addressed-to-the-bay-that-has-focus-and-a-global-letter-is-a-convenience-or-the-operators-own.md) dissolves it rather than picking a winner: the keyboard is addressed to the bay that has focus, and those rows' badges stop naming letters at all. **Binding them in this bay would have been work thrown away**, so the four badges left behind are that record's to clear rather than work anybody skipped.
   - *(On 2026-09-08 two of the four cells stopped printing letters and read `&mdash;`, because every letter they printed was already bound in `crates/karakuri/src/main.rs`'s key match to something else — the `has` side won and the `plan` side was unreachable.)* The debt is restated beside M5.2's entry in [roadmap.md](../roadmap.md), where it is M5.13's.

6. **The bay's prose, as tooltips — done on 2026-09-03, re-opened the day the transition row was built, and done again on 2026-09-05**:
   - Two notes and half of a third — *Mixer*, *The mixer has no crossfader*, and the selection half of *Two focuses, and they do not look alike* — went onto the controls they describe. **Eleven tips on 2026-09-03**: the strip-count readout, deck A's strip (the selection, which is why the strip has no capsule of its own), three trims, three faders, three meters, deck B's pending-fade number, and the transition row, which carried the crossfader argument whole and said where the wipe's shape and soft edge come from. (That tip said they were open questions while they were, and was rewritten when they were answered.)
   - **It re-opened on 2026-09-05**, because `74719c3` and `094804c` drew four capsules the mock had no tip for — the shape pill, the quantum pill, the length pill and `go` — and **a bay whose prose is on its controls is a claim about the controls it has, not about the ones it had on the day it was closed.**
   - Four tips written the same day, **sourced rather than invented**: the three cycles and the words in them are `karakuri-console`'s `WIPE_SHAPES`, `QUANTA` and `FADE_BEATS`, and `go`'s two refusals are `TransitionRow::go`'s. The row's own tip kept the argument — the crossfader, the wipe this bay cannot draw, and the soft edge, which is no control's anywhere — and what each setting *means* moved down onto the pill that sets it, as did the two decks a wipe names and the two ways it is refused. **Moved and not copied**: the row's tip is 705 characters shorter and no sentence it lost is still on it.
   - The meters are the only ones not sourced from the notes, which say nothing about a meter: they come from [ADR-0043](../adr/0043-the-meter-never-waits-and-the-deck-owns-it.md) and [ADR-0178](../adr/0178-the-mixer-draws-four-tracks-and-as-many-strips-as-the-deck-has.md).

7. **And the tooltip pass found the mock drawing what ADR-0178 rejected**:
   - The fourth track carried a whole empty strip — a name, a `tally off`, a trim, a fader and a meter — and that record's *Alternatives rejected* is precisely *"a well per track, empty where no deck fills it … A track nothing fills draws nothing at all"*, on the grounds that an empty strip asserts *there is a deck here and it is at zero*. `karakuri-console`'s `tests/mixer.rs` already held the panel to the record and said so against the mock.
   - **Four tips for that strip were written and then removed rather than kept**: a tooltip is what an operator reads, and one on a control the panel is decided never to draw is a reading nobody can take.
   - **The mock lost that strip on 2026-09-05**, which was a change to a designed page and this bay's rather than a tidy-up; `.tally.off` went with it, the one rule in `docs/manual/style.css` nothing else used.

#### M5.2 Exit, met on 2026-09-05

- **No `plan` badge in the panel column of this bay's rows**, and it is a grep rather than a judgement: no row of this bay carries one. *Fade a deck out or in* and *Crossfade to the next deck* read `gap`; *Wipe the next deck in* and *Choose the wipe shape, the quantum, the length* read `has` against the transition row; the strip's gain, opacity, blend mode and mask mini were already `has`.
- **What it drew on the way** is the transition row, which was painted by nothing; **what it stopped drawing** is the mock's fourth strip, which a record had rejected; and **what it decided** is that a fade has no control on a strip.

- **The mixer's under-draw.** *Set a deck's mask position* carries no `plan` badge in either column and is in no exit condition. It is named in [ADR-0206](../adr/0206-a-fader-marks-where-it-is-going-and-keeps-reaching-for-it.md), and whatever surface gives the mask's front a position closes it. Tracked in [roadmap.md](../roadmap.md).
